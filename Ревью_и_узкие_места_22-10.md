## 3. Агент как агент: цикл гипотез почти не работает

Данные `agent_journal.jsonl`, 196 гипотез по всем прогонам с LLM, старый код:

| Статус | Доля |
|---|---|
| отклонено | 71% |
| невалидно | 6% |
| вето критика | 6% |
| **принято** | **3,6% (7 гипотез)** |

На трёх из пяти свежих прогонов принято 0 из 25. Holdout с LLM и без не отличается: reg_h5 29,69 против 28,9–29,5, cls_shift 0,5788 против 0,5789. Цикл стоит до 60 минут и 260–300 тыс. токенов. Вызовы LLM занимают 51–84% времени цикла.

Причины, найденные в коде и логах:
- **Правило принятия на трёх временных фолдах требует выигрыша на всех трёх.** Условие «не хуже на 70%» при трёх фолдах означает 3 из 3. Отклонены гипотезы со средним улучшением 2–4% (reg_h5 #14: 46,61 против 48,45, лучше на 2 фолдах из 3). На пяти фолдах то же правило, наоборот, слишком мягкое (п. 13).
- **Ошибка оценки записывается как «rejected»** (`solution.py:251-256`): LLM видит в журнале проверенную и отвергнутую гипотезу, хотя та упала.
- **Нет дедупликации.** Повторы ловит только критик по последним 15 записям. В логах `ent_last/(HDD+CDD+1)` дважды, три почти одинаковых `group_mean`, `drop` уже удалённых колонок.
- **Критик ошибается.** Он отверг `group_mean(sbytes) по service` как утечку таргета и `path_smooth` как несуществующий параметр LightGBM, а `path_smooth` есть в документации.
- **LLM видит мало.**
  - Срезы ошибок только по категориям до 60 значений, без числовых колонок.
  - Только первые 80 колонок: новые признаки стоят в конце и на широких данных не видны.
  - Текстовые колонки после замены на OOF исчезают из профиля.
  - Нет важности признаков и пофолдовых дельт самой гипотезы.
  - В схеме ответа нет поля «что я заметил и какой эффект жду», поэтому отчёт не показывает связку «наблюдение → гипотеза → результат». Это именно то, что кейс называет агентностью.
- **Аналитик «подтверждает» без проверки.** `leak` и `noise` получают ok без проверки. Роль `id` даётся по ≥95% уникальных, и под неё попадает любая непрерывная float-колонка. Все бесполезные колонки удаляются одним экспериментом: одна полезная в списке срывает всё удаление.

Что говорят источники:
- MLAgentBench: около 20% прогонов «галлюцинировали» улучшение, а длинные прогоны обычно ухудшают метрику (ar5iv.labs.arxiv.org/html/2310.03302).
- LLM-FE: без итеративного уточнения качество выходит на плато через 5–7 итераций (arxiv.org/html/2503.14434v2).
- MARICL: LLM получает top-k примеров с наибольшим остатком и описания колонок, R² XGBoost растёт с 0,579 до 0,723 за 10 итераций (arxiv.org/html/2605.22897; пилотный препринт, малые датасеты).
- AIRA_2: разделить фолды поиска и фолды выбора финала, скрыть от агента метки валидации отбора (arxiv.org/abs/2603.26499, по аннотации).
- «Format tax»: строгий структурированный вывод снижает качество рассуждения open-weight моделей. Помогает сначала рассуждать свободным текстом, потом форматировать (arxiv.org/abs/2604.03616, по аннотации).

## 4. Время

По логам стенда (платформа примерно в 1,5 раза медленнее):
- **CatBoost съедает 40–90% прогона:** s_diamonds 597 из 669 с, s_house 133 из 153 с на 1 тыс. строк, reg_h4 489 из 825 с. При этом он лучший одиночный кандидат на holdout в 5 задачах из 14, выкидывать его нельзя. Документация CatBoost советует для CPU `boosting_type=Plain`, `bootstrap_type=Bernoulli` с `subsample<1`, `leaf_estimation_iterations` 1–5, `max_ctr_complexity` ≤2, колонки как `pandas.Categorical`. `border_count` на CPU скорость почти не меняет (catboost.ai/docs/en/concepts/speed-up-training).
- **Дубли:**
  - `lgb` в зоопарке повторяет ядро до знака: s_letter 149 из 1066 с.
  - Для RMSLE и MAPE `lgb` и `lgb+log1p` совпадают и дважды входят в ансамбль.
  - Линейная модель рефитится на 5 seed, хотя она детерминирована.
- **Порядок зоопарка.** В регрессии медленный `lgb_fine` стоит восьмым из 16, а не последним: план перебирает модели внутри каждого преобразования таргета.
- **Масштаб.** Линейная экстраполяция: при данных в 5–10 раз больше один зоопарк без LLM займёт 100–200 минут на платформе. На зоопарк по коду остаётся около 80 минут. Это оценка, не замер.
- **s_letter** (14 тыс. строк, 26 классов) — пик памяти 4,5–5 ГБ.

## 5. Качество

- **Варианты на остатке и линейные варианты вредят:**
  - на reg_h4 `+resid` лучше по OOF, но хуже на holdout (lgb 31,9 против 35,6, lgb_slow 31,8 против 39,3);
  - `linear+resid` даёт RMSE 208–367;
  - медиана это переживает, но тащит около 16 кандидатов-пустышек.
- **Малые данные:**
  - s_wine хуже RF: итог 0,644 при ET 0,625 на holdout;
  - s_phoneme хуже RF;
  - на s_moneyball лучшая — линейная модель, а смесь её разбавляет.
- **Обрезка диапазоном train для всех семейств** (`core.py:185-187, 207-210, 413`) режет законную экстраполяцию тренда при прогнозе следующего периода. Нужна только линейной модели.
- **Множители классов** дают весь выигрыш на cls_shift (0,52 → 0,58–0,59), но нестабильны: вес Generic от 0,03 до 0,22 между прогонами. В `fit_weights` база обновляется внутри перебора, поэтому сетка накапливается до 3^k вместо 0,33..3 [код].
- **Положительный класс бинарной задачи** выбирается по редкости на каждом фолде заново (`metrics.py:28-35`). При классах около 50/50 он может меняться между фолдами [код].
- **inf и числа больше 3,4e38** ломают ExtraTrees и линейную модель (`core.py:299`, float32), и обе молча выпадают из зоопарка [код].
- **MAPE при отрицательном таргете:** log1p не включается, и модели учатся на сыром L2 [код].
- **Сдвиг и холодный старт, по источникам.** У WiDS 2022, 1 место, отдельная модель для зданий без истории и псевдометки из первой модели (Kaggle writeup, по пересказу поиска). DomainBed и TableShift: выбирать модели по leave-one-group-out по сдвинутой колонке, а не по общему OOF. DRO для GBDT не покупать (arxiv.org/html/2312.07577v3).
- **Label shift, по источникам.** EM без калибровки проигрывает BBSE и RLLS. Нужна калибровка BCTS и априоры как среднее калиброванных OOF, а не доли меток (ar5iv.labs.arxiv.org/html/1901.06852). Наши три проверки EM не помогли. Нужно сверить, брались ли априоры именно так.

- `out.to_numpy()` у Series из кода LLM теряет индекс (`research.py:232`).
- Подстроки `import`, `eval`, `exec`, `__` в именах колонок отклоняют нормальные гипотезы.
- В отчёт не пишется код гипотез, отчёт невоспроизводим. `report.trials` заполняется только после цикла.
- Логистическая регрессия текстовой ветки без ограничения времени (`text.py:57`).
- `bench/metrics.py:51`: деление на ноль, если прокси-бейзлайн даёт метрику 1,0.
