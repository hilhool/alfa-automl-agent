# **Проект: ИИ-агент для разработки ML-моделей (версия 2\)**

## **1\. Условия кейса**

> * Агент получает описание задачи и CSV (train.csv, test.csv, data\_dictionary.csv, sample\_submission.csv), сам строит модель и пишет файл предсказаний.  
> * Сдаём ZIP, в корне solution.py. Интерфейс, переменные окружения и формат вывода как в baseline.py. 3 сабмита в сутки, сброс в 00:00 МСК.  
> * Проверка: Docker, Python 3.12, 8 CPU, 32 GB RAM, без интернета, до 3 часов на задачу, потом процесс убивают.  
> * Только данные кейса и библиотеки из requirements.txt, предобученные модели нельзя.  
> * LLM: Qwen3.8-27B через API организаторов, свои ключи нельзя. На разработку 600 руб в день на команду.  
> * Public: регрессия (site\_eui, RMSE, 53 308 строк train) и мультикласс (attack\_cat, Macro F1, 87 670 строк train). Private: две новые задачи, метрики не раскрывают.  
> * Балл считают относительно бейзлайна, результат не лучше бейзлайна даёт 0\. Итог равен среднему по двум задачам.  
> * Для private платформа берёт версию с лучшим public score и запускает её без изменений.
> * Балл из приложения 3: S\_reg = 100 · max(0, 1 − RMSE / B\_RMSE), S\_cls = 100 · max(0, (F1 − B\_F1) / (1 − B\_F1)), где B — метрика бейзлайна на том же test. Score = (S1 + S2) / 2. Для регрессии 50 баллов означают RMSE вдвое ниже бейзлайна.
> * Задачи запускаются по отдельности, файлы между ними не передаются. Платформа не возвращает агенту скор, валидацию он строит сам.

## **2\. Что мы нашли в данных**

Прогнали pandas по обоим датасетам. Три вещи меняют план.  
**Регрессия.** Весь test относится к Year\_Factor \= 6, в train только годы 1–5. Получается прогноз на следующий год, и обычный KFold будет показывать качество лучше реального. Штаты в test распределены иначе, energy\_star\_rating пропущен в 20% строк против 42% в train.  
Здания повторяются по годам. Если склеить State\_Factor, building\_class, facility\_type, floor\_area, year\_built и ELEVATION, у 37,7% строк test это здание уже встречалось в train. Внутри одного здания std таргета 11,3, по всему train 58,7. Прошлые значения здания дают очень сильный признак.  
*Уточнение на этапе 1:* ELEVATION у одного здания меняется между годами (первая строка test: 13,1, то же здание в train: 2,4). Без ELEVATION в ключе у 79,1% строк test здание есть в train, std таргета внутри ключа 11,0. Ключ из пяти колонок покрывает вдвое больше test.  
Константа-среднее на отложенном Year\_Factor = 5 даёт RMSE 56,8. RandomForest по умолчанию даёт 57,4, линейная регрессия 73,4: сдвиг по годам ломает простые модели. Если бейзлайн платформы тоже простой, планка по RMSE низкая, но 1 − RMSE/B требует уронить ошибку в разы.  
**Мультикласс.** 38% строк train полностью повторяют другие строки по признакам. У 14,8 тыс. строк признаки одинаковые, а метки разные, чаще всего Exploits и DoS. Если для каждого набора признаков брать самую частую метку, macro F1 на самом train выходит 0,815, выше этого на таких признаках не прыгнуть. В статьях по UNSW-NB15 реальный уровень около 0,55–0,63.  
С train совпадают только 3,5 тыс. из 41 тыс. строк test. Похоже, test взят из официального testing-set, где распределение другое. В test есть значения state (ACC, CLO), которых нет в train. id перемешан, утечки через него нет.

## **3\. Что говорят статьи**

> * SELA (агент с MCTS) на 20 датасетах набрал 53,3%, AutoGluon 53,2%. Перебирать модели и гиперпараметры через LLM смысла нет, AutoGluon справляется сам. LLM полезен там, где нужен смысл колонок.  
> * MLE-STAR (Google) считает ablation, находит блок кода, который сильнее всего влияет на метрику, и правит только его. На одной и той же модели 43,9% медалей против 25,8% у AIDE. У них же проверка на утечку: в одном примере val вырос с 0,819 до 0,868, а test упал с 0,803 до 0,734.  
> * AIRA-dojo (Meta): если брать финал по максимуму на валидации, теряется 9–13 п.п. При долгом поиске качество сначала растёт, потом падает. Помогает брать несколько лучших кандидатов.  
> * AutoKaggle: после добавления юнит-тестов на формат доля доведённых задач выросла с 0,10 до 0,85.  
> * METR: o3 взламывал скоринг в 30% прогонов RE-Bench, фраза «не жульничай» в промпте почти ничего не меняла. Код оценки агенту трогать нельзя.  
> * KompeteAI ускоряет оценку кандидатов и за то же время успевает в 7 раз больше итераций.  
> * CAAFE: LLM придумывает признаки по описанию колонок, средний ROC AUC вырос с 0,798 до 0,822 на 14 датасетах.  
> * AutoMind: без базы готовых приёмов win rate падает на 11,8%. DS-Agent: слабой модели лучше давать один пример в промпте, несколько ухудшают результат.  
> * В autogluon 1.3.1 нет RealMLP и TabM, они появились в 1.4. pytabkit в requirements нет. Пресет experimental\_quality скачивает TabPFNMix, без интернета не заработает. В коде пресета прямо написано «Uses pre-trained tabular foundation models», а предобученные модели запрещены условием. Не используем.

## **4\. Принципы**

> 1. **Валидный сабмит первым.** На диске всегда лежит корректный файл. Пишем во временный файл и переименовываем, чтобы kill посреди записи не оставил битый CSV.  
> 2. **Ядро работает без LLM.** Если API лёг или отвечает мусором, пайплайн всё равно доходит до хорошего результата.  
> 3. **Валидация повторяет устройство test.** Схему CV выбираем по тому, чем test отличается от train: по времени, по группам или стратифицированно. Случайный KFold только когда сдвига нет.  
> 4. **LLM отвечает за смысл, перебор делает код.** LLM разбирает задачу, роли колонок, метрику и предлагает признаки. Модели и гиперпараметры перебирают AutoGluon и Optuna.  
> 5. **Код оценки закрыт.** Разбиение, метрика и holdout лежат в модуле, который LLM не видит и не меняет.  
> 6. **Финал собираем ансамблем** из нескольких лучших кандидатов по OOF, одного победителя не берём.  
> 7. **Ничего под конкретный датасет.** Колонки, таргет, id и метрику определяем из task.md, data\_dictionary.csv и sample\_submission.csv.

## **6\. Блоки подробно**

### **6.1. Разбор задачи и метрики**

Поддерживаем RMSE, MAE, R², accuracy, F1 (macro, weighted, binary), AUC, logloss. Для неизвестной метрики LLM пишет функцию или выбирает её из sklearn. Перед использованием прогоняем тест: идеальное предсказание должно получить лучший балл, чем случайное, и направление (больше или меньше лучше) должно совпасть. Не прошла тест, берём метрику по умолчанию для типа задачи.

### **6.2. Выбор схемы валидации**

> * Ищем колонки, у которых значения в test не встречаются в train. Если колонка похожа на период (Year\_Factor), валидируем по времени: учимся на прошлых периодах, проверяем на последнем.  
> * Adversarial validation: учим классификатор отличать train от test. Если AUC заметно выше 0,5, смотрим, какие признаки сдвинуты, и учитываем их в разбиении.  
> * Если есть повторяющиеся сущности или полные дубли, делаем GroupKFold по ключу.  
> * Иначе стратифицированный KFold, для мультикласса с учётом редких классов.  
> * Фолды фиксируем один раз. Все модели и все эксперименты считаются на одних фолдах, иначе ансамбль и подбор весов поедут.  
> * Отдельно откладываем holdout (последний период или 10–15% групп). Цикл его не видит. Открываем 5–10 раз за прогон, ответ только «стало хуже или нет», без точного числа. *(22.10: в коде не реализовано, все шаги принимаются на одних фолдах. См. ревью в журнале.)*

### **6.3. Повторяющиеся сущности**

Агент перебирает наборы колонок, которые не меняются у одной сущности между периодами: категории, площади, годы постройки, координаты. LLM подсказывает кандидатов по описанию из data\_dictionary, код проверяет: ключ должен повторяться в разных периодах, а таргет внутри ключа должен разбрасываться меньше, чем по всем данным.  
Нашли ключ, добавляем признаки по прошлым периодам этой сущности: среднее и последнее значение таргета, число наблюдений, тренд. Считаем строго по прошлому относительно строки, на валидации тоже. На регрессии это самая перспективная идея.

### **6.4. Конфликтующие дубли и потолок качества**

Группируем строки по всем признакам и считаем, сколько групп с разными метками. По самой частой метке в группе получаем грубый потолок метрики. Агент сравнивает с ним текущий скор и понимает, есть ли куда расти. Ещё пробуем признаки: размер группы одинаковых строк в train+test и OOF-распределение меток внутри группы.

### **6.5. Цикл AutoResearch**

> 1. LLM получает короткую сводку: данные, текущий лучший скор, потолок, последние 5–10 записей журнала, таблицу ablation по группам признаков.  
> 2. Выбирает действие из меню и отвечает JSON по pydantic-схеме. Признаки описывает на мини-языке: ratio, diff, log, group-агрегат, части даты, порог. Произвольный код пишет только если меню не хватает, и такой код запускается в песочнице с таймаутом.  
> 3. Перед запуском проверка на утечку: признак не использует таргет вне fit, не трогает test-разметку и id, не коррелирует с таргетом почти идеально. *(22.10: в коде только Spearman > 0,995 для регрессии и бинарной задачи; агрегаты по производным колонкам `ent_*` не запрещены и дают утечку при валидации по времени.)*  
> 4. Считаем быструю оценку на зафиксированных фолдах.  
> 5. Решение по правилу ниже, запись в журнал: гипотеза, изменение, метрика по фолдам, решение, причина.

**Правило принятия.** Сравниваем с текущим лучшим парно по фолдам. Принимаем, если выполнено всё:

> * средняя разница больше 0,5–1 std разниц по фолдам;  
> * улучшение есть минимум на 70% фолдов;  
> * corrected t-test Nadeau–Bengio даёт p меньше 0,1 (используем как фильтр шума, а не строгий тест).

Чем больше экспериментов уже прошло, тем выше порог. Большинство гипотез будут откатываться, это нормально. *(22.10: в коде иначе — среднее лучше на 0,2% и не хуже на 70% фолдов, порог постоянный, t-test нет. На трёх временных фолдах это требует 3 из 3.)*  
**Меню действий:**

> * Предобработка: пропуски (NaN плюс флаг пропуска), кодирование категорий, лог-преобразования, даты.  
> * Признаки: частоты, взаимодействия, group-агрегаты, признаки по сущностям, признаки по смыслу из data\_dictionary, отбор признаков.  
> * Редкие классы: веса классов, SMOTE (в том числе только для части классов), объединение путающихся классов в иерархию.  
> * Сегментация: общая модель против отдельных по категории.  
> * Таргет: лог, обрезка выбросов, другая функция потерь (L1, Huber, Tweedie).

Для слабой 27B-модели держим в промпте статическую базу на несколько десятков проверенных приёмов и один рабочий пример ответа. Для коротких JSON-ответов выключаем thinking (enable\_thinking=false).

### **6.6. Тяжёлые модели**

> * AutoGluon best\_quality, eval\_metric под задачу, time\_limit по остатку бюджета. Свои фолды передаём через `TabularPredictor(label=..., groups="fold")`: параметр конструктора, не `fit`. Колонка содержит номер фолда, AutoGluon режет через LeaveOneGroupOut и не берёт её в признаки. Работает только с bagging. Проверено по исходникам 1.3.1, predictor.py.  
> * Свои CatBoost, LightGBM, XGBoost на 2–3 сидах на тех же фолдах, OOF сохраняем.  
> * Если AutoGluon упал, запускаем LightAutoML TabularUtilizedAutoML с cpu\_limit=8.

### **6.7. Финал**

> * Hill climbing по Caruana на OOF всех моделей под целевую метрику.  
> * Подстройка под метрику, подбираем на одних фолдах, проверяем на других:  
  * Macro F1: множители к вероятностям классов, подбор по координатам;  
  * binary F1: порог;  
  * лог-таргет при RMSE: поправка smearing при обратном переходе, и только если лог выиграл на OOF;  
  * MAE: regression\_l1;  
  * logloss: sigmoid-калибровка; AUC не трогаем.  
> * Финальная проверка на holdout против простого бейзлайна. Хуже бейзлайна, откатываемся к ядру.  
> * Рефит на всём train, для временного сдвига обязательно с последним периодом.

## **11. Журнал работ**

### Этап 1. Разбор baseline и локальный стенд (20.10.2026)

**Что делает baseline.py.** Запуск `python baseline.py task.md`, ключи берутся из `OPENAI_API_KEY`, `OPENAI_MODEL` и `OPENAI_BASE_URL`. Скрипт поднимает MCP-сервер с одним инструментом `run_python` и до 100 шагов гоняет Qwen с системным промптом «предложи самую простую ml-модель». Сабмит baseline сам не пишет, его пишет код от LLM. Отсюда интерфейс для solution.py:

> * один аргумент, путь к task.md;
> * ответ кладём в `submission.csv` рядом с task.md: так сказано в task.md, туда же смотрит cwd инструмента у baseline;

В task.md записаны `regression/participants/train.csv` и `multiclass/participants/train.csv`, а в выданном нам архиве файлы лежат рядом с task.md. Значит, на платформе раскладка с подкаталогом, и для private подкаталог может называться иначе. Ищем по путям из task.md, потом по имени файла во всём каталоге.

**Находки в baseline.py и requirements.txt.**

### Зоопарк моделей, медиана для регрессии, правило принятия с порогом (21.10.2026)

### LLM в агенте: метрики, цикл AutoResearch (21.10.2026, вечер)

Пользователь решил, что агент должен по-настоящему опираться на LLM, а не только на правила. Сделано три вещи.

**Словарь метрик.** Private придёт с неизвестной метрикой, поэтому `spec.METRIC_PATTERNS` теперь знает rmse, mae, r2, rmsle, msle, mape, smape, medae, f1\_macro, f1\_weighted, f1\_binary, accuracy, balanced\_accuracy, mcc, kappa, qwk, roc\_auc, gini, pr\_auc и logloss, по-русски и по-английски (16 формулировок проверены, публичные задачи по-прежнему rmse и f1\_macro). Для каждой есть направление, реализация в `metrics.py` и подходящий objective: mape идёт в objective mape, MAE-подобные в l1. Для rmsle и msle предсказание обрезается снизу нулём, классовые множители подбираются и под mcc, kappa, qwk и balanced accuracy. Если регулярки метрику не нашли, её спрашивают у LLM и принимают ответ только из списка.

**Клиент LLM** (`agent/llm.py`). Прокси организаторов управляет рассуждением Qwen через `extra_body={"reasoning": {...}}`, как OpenRouter. Без параметра модель тратит весь `max_tokens` на рассуждение и возвращает пустой content. `effort: low` даёт около 2600 токенов рассуждения и 30–40 с на ответ, `enabled: false` — 165 токенов и 5 с. `enable_thinking` и `reasoning_effort` прокси игнорирует. json\_schema работает, но необязательные поля модель пропускает, поэтому все поля схемы обязательные. Четыре неудачи подряд — LLM выключается, агент идёт без неё.

**Цикл AutoResearch** (`agent/research.py`). На каждой итерации LLM получает task.md, колонки с описаниями из data\_dictionary, текущий скор, срезы ошибок (худшие категории для регрессии, главные пары путаницы для классификации) и журнал прошлых гипотез. Она предлагает одну гипотезу: ratio, diff, product, group\_mean, group\_std, group\_count, freq, drop или произвольный код на pandas/numpy. Код идёт в песочницу без импортов и с таймаутом 60 с, признак с |Spearman| к таргету выше 0,995 отбрасывается как утечка. До 12 гипотез, цикл не дольше 45 минут от старта, оценка гипотезы обрывается через 55 минут.

На стенде прокси не доходил до API: `run.py` не передавал HTTP(S)\_PROXY в дочерний процесс. Добавили в `PASS_ENV`.
