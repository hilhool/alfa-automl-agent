### Балл (приложение 3)

- `S_reg = 100 · max(0, 1 − RMSE / B_RMSE)`
- `S_cls = 100 · max(0, (MacroF1 − B_F1) / (1 − B_F1))`
- Итог `(S1 + S2) / 2`. B — метрика бейзлайна на том же test. Результат не лучше бейзлайна даёт 0.
- Скор бейзлайна платформы неизвестен. Бейзлайн — это Qwen, которая пишет «самую простую модель», так что он плавает от прогона к прогону. Локально вместо него два прокси: линейная модель и RandomForest.

## Данные публичных задач

### Регрессия: site_eui, RMSE

- train 53 308 × 64, test 22 449 × 63. Признаки: Year_Factor, State_Factor, building_class, facility_type (60 категорий), floor_area, year_built (есть 0 и NaN), energy_star_rating, ELEVATION, 36 помесячных температур, 18 погодных показателей. Погода относится к тому же году, что и таргет.
- **Весь test — Year_Factor = 6, в train годы 1–5.** Это прогноз на следующий год, случайный KFold врёт.
- energy_star_rating пропущен в 41,7% строк train и в 20,0% строк test. Распределение штатов в test другое.
- Здания повторяются по годам. Ключ `State_Factor, building_class, facility_type, floor_area, year_built` **без ELEVATION** (у одного здания она меняется между годами) находит здание в train для 79,1% строк test. Std таргета внутри ключа 11,0, по всему train 58,7. Признаки по прошлым годам здания — главная идея для регрессии (этап 3). С ELEVATION в ключе покрытие всего 37,7%.
- В data_dictionary сказано, что id не подтверждён как постоянный идентификатор здания.

### Мультикласс: attack_cat, Macro F1 (UNSW-NB15)

- train 87 670 × 44, test 41 166 × 43. 10 классов: Normal, Generic, Exploits, Fuzzers, DoS, Reconnaissance, Analysis, Backdoor, Shellcode, Worms. Категориальные колонки: proto, service, state (`-` означает отсутствие сервиса).
- Test — стратифицированные 50% официального hold-out split UNSW-NB15. Колонку `label` убрали как утечку.
- Полные дубли по признакам: 44,8% строк имеют двойника (38% — «повтор другой строки»). У 14 829 строк признаки совпадают, а метки разные, чаще всего Exploits и DoS. Потолок macro F1 по моде группы на самом train около 0,815. В литературе реальный уровень 0,55–0,63.
- Только около 3,5 тыс. из 41 тыс. строк test совпадают с train. В test есть значения state (ACC, CLO), которых нет в train. Доля Normal в train 31,9%. Сдвиг долей классов в test вероятен (по памяти, в официальном testing-set Normal около 45%, не проверено). id перемешан, утечки через него нет.

## Архитектура агента (план, подробно в проектном md, разделы 4–7)

Принципы, которые нельзя нарушать:
1. На диске всегда лежит валидный сабмит. Запись через tmp + `os.replace`.
2. Ядро работает без LLM. Лёг API — пайплайн всё равно доходит до результата.
3. Валидация повторяет устройство test: время, группы или стратификация.
4. LLM отвечает за смысл (роли колонок, признаки по описанию, гипотезы). Модели и гиперпараметры перебирают код, AutoGluon и Optuna.
5. Код оценки (фолды, метрика, holdout) LLM не видит и не меняет. Защита от reward hacking.
6. Финал — ансамбль нескольких кандидатов по OOF (Caruana hill climbing), а не один победитель.
7. Ничего под конкретный датасет. Всё выводится из task.md, data_dictionary.csv и sample_submission.csv. Подгонку под public не сабмитим: та же версия пойдёт в private.

Тайминг на 3 часа: 0–5 мин разбор задачи, 5–15 мин профиль, CV, LightGBM и первый сабмит, 15–80 мин цикл AutoResearch на быстром LightGBM, 80–160 мин тяжёлые модели (AutoGluon best_quality со своими фолдами, CatBoost, LGBM, XGB на нескольких сидах), 160–170 мин ансамбль, подстройка под метрику, рефит, запись. Watchdog около 170 мин.

Правило принятия гипотезы в цикле: парное сравнение по фолдам. Средняя разница больше 0,5–1 std разниц, улучшение минимум на 70% фолдов, corrected t-test Nadeau–Bengio p < 0,1. Порог растёт с числом экспериментов.

Цепочка fallback: полный пайплайн → ядро без LLM → константа (среднее или мода).

## Текущее состояние кода

`solution.py`: `locate` → константа пишется сразу → `spec.parse` → `cv.make_folds` → `core.run_core` → проверка → атомарная запись поверх константы. Исключение в ядре ловится, константа остаётся.

- `taskio.locate`: ищет CSV сначала по путям из task.md (относительно его каталога), потом `<task_dir>/<name>.csv`, потом `rglob` по имени, берёт самый мелкий по глубине. submission.csv пишется рядом с task.md. Риск: на платформе наш код лежит в том же каталоге, и rglob может зацепить чужой `train.csv`. Поэтому в ZIP не должно быть никаких CSV.
- `taskio.check_submission`: колонки как в sample, число строк, id совпадают с test по значениям и порядку, нет дублей, NaN и inf, нет классов вне train.
- `spec.parse`: target и id берёт из колонок sample_submission. Регрессия, если таргет числовой и (есть дробные значения или больше 50 уникальных), иначе binary или multiclass. Метрику ищет регулярками по task.md, при несовпадении с типом задачи берёт метрику по умолчанию: rmse / f1_binary / f1_macro. `proba_output` включается только для roc_auc и logloss при числовом шаблоне.
- `cv.make_folds`: (1) колонка-период: целая, 2–50 значений, в test только значения не меньше максимума train и есть новые → валидация вперёд по 3 последним периодам; (2) больше 10% полных дублей → StratifiedGroupKFold (для регрессии GroupKFold) по хешу строки; (3) иначе StratifiedKFold или KFold на 5 фолдов, seed 0. Сделано: регрессия → time_forward по Year_Factor, мультикласс → group_dups.
- `metrics.evaluate`: на вход вероятности (n, k) в порядке `spec.classes`, `to_labels` берёт argmax с опциональными весами классов. Для binary F1 положительным считается более редкий класс.
- `core.run_core`: строковые колонки в pandas category с общим словарём train+test. LightGBM: lr 0.05, 63 leaves, early stopping 100, до 5000 раундов, 8 потоков. Рефит на всём train с числом раундов `mean(rounds) × 1.1`.

`run.py` собирает ZIP (или берёт `--zip`), копирует `bench/tasks/<name>` в `bench/runs/<name>_<время>/`, распаковывает туда ZIP и запускает `python solution.py task.md` с cwd в этом каталоге, как платформа, привязывает процесс к 8 логическим ядрам, меряет пик RSS, по таймауту убивает всё дерево процессов, проверяет формат и считает метрику и балл по `answers/<name>.json`. Передаёт только PATH, SYSTEMROOT, TEMP, TMP, USERPROFILE, HOME и OPENAI_*, плюс `code/.env`. Лог прогона в `runs/<...>/run.log`, лог агента в `runs/<...>/agent.log`.

## Сборка ZIP

`bench/build_zip.py` кладёт в `dist/solution.zip` только `solution.py` и `agent/*.py`, компилирует каждый файл и падает, если в архив попал CSV, `.env` или `__pycache__`. Любой прогон `run.py` идёт через этот ZIP, распакованный в каталог задачи. Перед сабмитом: `run.py` на всех задачах стенда и `grep -ri claude` по `code/` без `.venv` (проверку упоминаний в скрипт не встроили, иначе слово оказалось бы в самом коде).
